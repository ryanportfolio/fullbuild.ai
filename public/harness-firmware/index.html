When the agent hits a problem, you type /recall in the agent and it writes the lesson into a file in your repo. Every session after that reads it at startup. Because the file is committed, your teammates' agents get it too.

04
HOW IT IS BUILT · image end 0x2ABFE

Not a pile of prompts

The small context bill is a side effect. The reason to run it is that every part follows a practice that holds up when the library and the team grow.

  1. Descriptions route, they do not summarise Every skill's front matter says when to use it, never what it does. That one line is all the agent sees until it opens the file, so it has to work as a classifier.
  2. Disclosure is progressive The index stays in context. The playbook is read only when the work matches it, through an ordinary file read.
  3. Skills are tested before they ship A new or edited skill is run against a fresh agent under pressure first, and the rule is blunt: no skill without a failing test. A skill is executable behaviour, not documentation.
  4. Memory has a system of record Lessons land in a named file that is committed, not in a chat log, so a later session or a teammate can replay where a fact came from.
  5. Claims are verified, not assumed The kernel forbids reporting a check that was not actually run, and requires saying so plainly when verification has to happen somewhere else.
  6. Restraint is enforced New rules and skills have to earn their place. Pruning stale content beats accreting it, because a library nobody trims stops routing correctly.
